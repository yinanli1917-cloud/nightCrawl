# nightCrawl gap analysis — 37 verified gaps (2026-06-19)

Source: ultracode Workflow `nightcrawl-gap-analysis` (42 agents, 5 dimensions, find then adversarial-verify). **37 confirmed, 0 false positives.**

Note: #1 (auto never routes to Engine R) is a DESIGN FORK — CLAUDE.md item 17 says routing is 'Advisory — never silently switches engines', so it may be intended. The data-honesty gaps (#2/#3/#21) are unambiguous bugs regardless.

## decision-lifecycle

### [HIGH] The "learned router" can never actually route to Engine R — auto only ever advises, dispatch is gated solely on the agent's explicit body.engine==='real'
- **Where:** `stealth/browser/src/server.ts:1957`
- **Evidence:** Dispatch: `if (body?.engine === 'real' && isBridgeCommand(body?.command) && bridgeHub.isConnected()) { return await routeToBridge(...) }` then unconditional fallthrough `const resp = await handleCommand(body, token); return await appendEngineGuidance(...)`. The only consumer of the journal recommendation is `buildNavGuidance` (server.ts:1430), which produces a TEXT block. cli.ts:499 defaults `cliEngine='auto'`. There is NO code path where `recommendForDomain`/`advise` resolves `auto` into a `real` dispatch — grep of server.ts+cli.ts for `recommendForDomain`/`recommendation` feeding dispatch returns only the guidance-formatting site. So on the default `auto`, even when the journal has learned `real` is 5/5 and headless times out 4/6 on a domain, the command STILL runs headless and merely prints 'recommended: real'. The 'learned router' is a learned *advisor*; the loop cannot self-correct execution, only the agent re-reading text and manually re-issuing `--engine=real` can.
- **Proposed fix:** Make `auto` honor a STRONG or sufficiently-confident learned recommendation at the dispatch boundary: before the headless fallthrough, if `body.engine==='auto'`, compute `advise(gatherSignals(url))` + `recommendForDomain(url)`; when the result is `real` with strength 'strong' OR confidence 'learned', and `isBridgeCommand && bridgeHub.isConnected()`, route to `routeToBridge`. Keep it advisory-only for weak/thin and when the bridge is offline (fall back to headless and say so). Record the realized engine in the journal so the loop closes.

### [HIGH] Engine R goto/snapshot can never record ok=false for a login wall — the bridge returns a fixed success string and never runs the daemon's wall-detection, structurally biasing the journal toward 'real'
- **Where:** `stealth/extensions/nightcrawl-bridge/background.js:283`
- **Evidence:** Bridge goto: `await waitForLoad(tabId); ...; return \`navigated to ${args[0] || ''}\`;` — a fixed success string, no login-wall detection. `recordEngineOutcome` keys `ok` off the response text: `const reloginRequired = /LOGIN_REQUIRED|CONSENT_REQUIRED/.test(text)` (server.ts:1385) and `ok: status === 200 && !reloginRequired` (server.ts:1393). Those tokens are injected ONLY on the headless path (server.ts:1236 `result += "\nLOGIN_REQUIRED..."`, 1241 `CONSENT_REQUIRED`). routeToBridge records `recordEngineOutcome(body, 'real', 200, text, ...)` where text='navigated to ...' (server.ts:1484), so a real-browser goto onto a login wall is always logged ok=true. Same for snapshot (bridge returns raw CDP a11y, no wall wrapper). recommendFromStats ranks by successRate first (engine-journal.ts:169), so Engine R's structurally-inflated success rate wins before the latency tiebreaker is even consulted. The router learns from poisoned data.
- **Proposed fix:** Run login-wall/consent detection on the bridge result path too, or have routeToBridge post-check the real browser's current URL/DOM for a wall (reuse the headless detector against the bridge's reported `bound.url`) and inject LOGIN_REQUIRED into `text` before `recordEngineOutcome`. Minimum viable: in routeToBridge, after goto, query bridge for final URL and run the same `detectLoginWall` used at server.ts:1236 so both engines feed comparable ok/relogin signals.

### [MEDIUM] Pure exploitation: ranking always returns ranked[0] with zero exploration, so once one engine wins a domain the alternative is never re-sampled and a better engine can't be discovered
- **Where:** `stealth/browser/src/engine-journal.ts:173`
- **Evidence:** `const best = ranked[0];` (engine-journal.ts:173) — deterministic argmax over successRate→latency→timeouts, no epsilon, no periodic probe, no confidence-interval overlap check. grep for `explore|epsilon|probe|random|both engine` across engine-routing.ts/engine-journal.ts/strategy-advisor.ts returns nothing. Combined with finding `router-cannot-route-on-auto` (auto never routes to real anyway), headless wins a domain on its first success, `auto` keeps it on headless forever, `real` is never recorded again for that domain, and `real`'s 0-sample stat means it never even enters `candidates` (filter `s.attempts > 0`, engine-journal.ts:165). The loop cannot discover that real is faster/more reliable unless the human/agent manually forces it.
- **Proposed fix:** Add bounded exploration: when the leader's advantage is within noise (e.g. successRate within a small margin AND the runner-up has < N samples), occasionally recommend the under-sampled engine (epsilon ~0.1, or a deterministic 'every Kth nav re-probe the alternative'). Alternatively use a UCB1-style score (successRate + c*sqrt(ln(total)/attempts_engine)) so under-explored engines get a bonus. Keep it advisory unless the dispatch fix lands.

### [MEDIUM] Journal aggregation weights all-time outcomes equally — the recorded `ts` is never used, and unlike domain-strategy there is no TTL, so a stale failure from months ago dilutes today's reality forever
- **Where:** `stealth/browser/src/engine-journal.ts:133`
- **Evidence:** `aggregateByEngine` (engine-journal.ts:133-156) groups by engine and computes successRate/median over the FULL record set; the `ts` field (defined engine-journal.ts:28, recorded server.ts:1389) is consumed nowhere in aggregation or ranking. There is no per-record TTL — contrast domain-strategy.ts:42 `ENTRY_TTL_MS = 30 days` with an explicit comment 'a site's bot posture can change; we'd rather re-learn'. The only eviction is `pruneJournal` (engine-journal.ts:108) capping at 5000 GLOBAL lines, domain-blind, so a low-traffic domain's months-old failures are never pruned. A site that fixed its bot wall last week still shows a depressed historical successRate and gets mis-routed.
- **Proposed fix:** Weight by recency in aggregateByEngine: either drop records older than a window (e.g. 30 days, mirroring domain-strategy) before aggregating, or apply exponential time-decay to each record's contribution to successRate/latency using `(now - ts)`. Cheapest correct fix: in recommendForDomain, pre-filter readDecisions to the last 30 days per domain.

### [MEDIUM] Engine R responses carry no guidance block at all — routeToBridge never calls buildNavGuidance, so an agent on the real browser never sees the routing recommendation, signals, or override hint
- **Where:** `stealth/browser/src/server.ts:1485`
- **Evidence:** routeToBridge returns `new Response(\`[real-browser] ${text}\`, ...)` (server.ts:1485) with no guidance appended. buildNavGuidance is invoked ONLY in appendEngineGuidance (server.ts:1430), which is reached only on the headless fallthrough (server.ts:1961). So the moment an agent successfully uses `--engine=real`, the 'enforced reminder the agent can't skip' (strategy-advisor.ts:11) silently goes dark — including any STRONG signal telling it to switch BACK to headless (e.g. a file-upload task, or the domain becoming hostile). The soft-enforcement channel is one-directional: headless→real advice is shown, real→headless advice is invisible.
- **Proposed fix:** Append the guidance block in routeToBridge too: after a successful bridge nav, compute `buildNavGuidance(url, 'real')` and append it to the returned text, mirroring appendEngineGuidance. Factor the guidance-append into a shared helper so both engine paths stay symmetric by construction.

### [MEDIUM] The journal records only the engine used + outcome, never the recommendation or whether the agent followed it — so the system can never reflect on whether its own advice was good (no counterfactual / regret signal)
- **Where:** `stealth/browser/src/engine-journal.ts:27`
- **Evidence:** EngineDecisionRecord (engine-journal.ts:27-38) has `engine` (used), `ok`, `latencyMs`, `timedOut`, etc., but NO `recommendedEngine`, NO `chosenBy` (auto-resolved | explicit | forced), NO `followedRecommendation` flag. recordEngineOutcome (server.ts:1371-1399) passes the used engine and never receives or stores the advice that was in effect. Result: aggregateByEngine can compute 'real succeeds 5/5 here' but can NEVER compute 'when we recommended real and the agent followed, outcomes improved vs when it overrode' — there is no recommended-vs-chosen pairing to learn from. The loop optimizes raw per-engine success, not advice quality, so a systematically-bad recommendation (see the ok-bias finding) is invisible to self-correction.
- **Proposed fix:** Extend EngineDecisionRecord with `recommendedEngine?: Engine`, `recommendationStrength?: 'weak'|'strong'`, `chosenBy?: 'auto'|'explicit'|'forced'`. Compute the recommendation at the route (you already build signals for guidance) and pass it into recordEngineOutcome. Then add an aggregation that measures recommendation regret (outcome when followed vs overridden) so the advisor can be audited and tuned from real data.

### [LOW] recordWin (domain-strategy memory) is called unconditionally on both engines even when the navigation was a login failure — domain memory disagrees with the honest journal
- **Where:** `stealth/browser/src/server.ts:1482`
- **Evidence:** routeToBridge: `if (url && url !== 'about:blank') { try { recordWin(url, 'real'); } catch {} }` (server.ts:1482) fires on ANY non-exception bridge result, with no `ok` check. Headless path does the same: `if (url && url !== 'about:blank') { try { recordWin(url, 'headless'); } catch {} }` (server.ts:1439) immediately after a `recordEngineOutcome` that may have set ok=false for a LOGIN_REQUIRED. `recordWin` in domain-strategy.ts:101-111 has no ok parameter at all. So a headless goto that returns LOGIN_REQUIRED is logged ok=false in the journal BUT recorded as a 'win' in domain-strategy. `rememberedEngine` (the advisor's weak prior, strategy-advisor.ts:119) then recommends the engine that actually failed. Two memory stores derive opposite conclusions from the same outcome.
- **Proposed fix:** Gate recordWin on real success. Have recordEngineOutcome return the computed `ok` (or compute it once at the route) and only call `recordWin(url, engine)` when ok===true. A login wall, timeout, or 502 must not count as a win for domain memory.

### [LOW] Thin (1-2 sample) learned recommendations are surfaced with the same authoritative reason text as fully-learned ones — the label says 'thin' but the 'why' still asserts it 'overrides the cold-start default'
- **Where:** `stealth/browser/src/engine-routing.ts:90`
- **Evidence:** When `learned` exists, engine-routing.ts:87-91 hardcodes `reason: 'Learned from past outcomes on this domain (overrides the cold-start default).'` regardless of `learned.confidence`. recommendFromStats returns confidence 'thin' for any winner with `attempts < MIN_LEARN_SAMPLES` (=3) (engine-journal.ts:182) — i.e. a SINGLE lucky sample produces a recommendation whose `why:` text claims it was 'Learned from past outcomes' and 'overrides the cold-start default'. The `recommended: real (thin)` label is shown (display.label, strategy-advisor.ts:205) but the prose contradicts it and reads as settled knowledge. An agent skimming the `why:` line over-trusts a coin-flip.
- **Proposed fix:** Branch the reason on confidence: for 'thin', say something like 'Tentative — only N sample(s) so far on this domain; recommendation may change as outcomes accrue.' Pass the sample count through LearnedRecommendation so the reason can cite it. Reserve 'Learned from past outcomes (overrides the cold-start default)' for confidence==='learned'.

## performance-timing

### [HIGH] Engine R goto timing out at the 15s load cap is silently swallowed — recorded as a fast success, never as timedOut
- **Where:** `stealth/extensions/nightcrawl-bridge/background.js:194-203, 281`
- **Evidence:** waitForLoad resolves (never rejects) on its 15s timer: `const timer = setTimeout(finish, timeoutMs)` with `finish = () => { ... resolve(); }` (background.js:198-200). After `await waitForLoad(tabId)` the goto unconditionally returns `navigated to ...` (background.js:281-283). So a page that never reaches status:complete in 15s returns a SUCCESS string with no error. Back in the daemon, routeToBridge records `recordEngineOutcome(body,'real',200,text,...)` (server.ts:1484) — ok:true, and recordEngineOutcome's `timedOut = /timeout/i.test(text)` (server.ts:1387) is false because the text is just 'navigated to ...'. Result: an Engine R goto that actually hit the load timeout is journaled as a successful ~15s nav with timedOut:false. Combined with the absent axTimedOut path, Engine R can never accumulate a timeout penalty on slow pages, while headless's 30s goto timeout DOES surface as 'timeout' text. The router's timeout-comparison is one-directional.
- **Proposed fix:** Have waitForLoad report whether it finished by completion or by cap (e.g. resolve a boolean), and have the goto branch append a marker like 'LOAD_TIMEOUT' to the returned text (or surface it in the tool_result payload) when the cap was hit. Then recordEngineOutcome's /timeout/i match (or a dedicated flag) will record timedOut:true for Engine R, restoring symmetry with headless.

### [MEDIUM] Headless and Engine R latencies measure fundamentally different pipelines — the cross-engine comparison is apples-to-oranges
- **Where:** `stealth/browser/src/server.ts:1937 / 1413 / 1484`
- **Evidence:** Both engines stamp `startedAt = Date.now()` at the same route boundary (server.ts:1937) and both compute latency as `Date.now() - startedAt` (headless at server.ts:1413 inside appendEngineGuidance; Engine R at server.ts:1484/1490 inside routeToBridge). But the work measured between those two stamps is NOT the same. The headless `goto` path runs a whole extra pipeline the bridge never does: the up-to-8s URL-settle loop (server.ts:1068-1087 `maxWait=8000, minWait=2000, stableFor=1500`), `browserManager.detectLoginWall()` (server.ts:1094), and on a wall it does cookie auto-import + a SECOND full `page.goto(targetUrl, {waitUntil:'load', timeout:30000})` (server.ts:1137) plus a 1.5s sleep + a re-detect. Engine R's `goto` only does `Page.navigate` + `waitForLoad` capped at 15s (background.js:194-203, 281) — no settle loop, no login-wall detection, no re-goto. So for the SAME domain, headless's recorded `latencyMs` is inflated by 2-10s of settle/detection work that Engine R's number simply omits. recommendFromStats (engine-journal.ts:168-172) then ranks `a.medianLatencyMs - b.medianLatencyMs` as a tiebreak, systematically biasing the router toward Engine R purely because its timer covers less work — not because the real browser is faster.
- **Proposed fix:** Make the recorded latency measure a comparable unit on both engines. Cleanest: stamp the headless latency at the point the navigation+load actually completes (right after the settle loop / before detectLoginWall), not after the entire login-wall+auto-import recovery pipeline, OR add a `phase` breakdown to EngineDecisionRecord (navMs vs recoveryMs) and have recommendFromStats compare only navMs. At minimum, exclude records where the login-wall recovery path ran (it has no Engine R counterpart) from the latency tiebreak, or tag them so they aren't compared head-to-head.

### [MEDIUM] axTimedOut (heavy-JS signal) can fire only on headless — Engine R snapshot returns raw HTML and never emits it, biasing the routing signal
- **Where:** `stealth/browser/src/server.ts:1386 vs extensions/nightcrawl-bridge/background.js:80`
- **Evidence:** recordEngineOutcome derives the heavy-JS timeout signal by string-matching the response text: `const axTimedOut = /accessibility snapshot unavailable/.test(text);` (server.ts:1386). That string is produced ONLY by the headless ariaSnapshot fallback (read-commands.ts:175, snapshot.ts:138). Engine R's `snapshot` maps to `evaluate('document.documentElement.outerHTML')` (background.js:80) — raw outerHTML, which can never contain 'accessibility snapshot unavailable'. So `axTimedOut` is structurally impossible to record for Engine R. Since aggregateByEngine counts `timeouts = r.timedOut || r.axTimedOut` (engine-journal.ts:144) and recommendFromStats uses fewer-timeouts as a ranking criterion (engine-journal.ts:170), a heavy-JS site that makes headless's AX snapshot time out will accrue timeout penalties on headless but Engine R gets a free pass on the same metric — even though Engine R may render the same heavy page just as slowly. The 'timeouts' axis is not symmetric across engines.
- **Proposed fix:** Either compute a heavy-JS signal for Engine R too (e.g. record the bridge's waitForLoad hitting its 15s cap as a timeout/heavy-JS marker — background.js:200 currently resolves silently on cap, losing that signal), or drop axTimedOut from the cross-engine ranking and keep it only as a within-engine diagnostic. The bridge should report whether waitForLoad finished by load-complete vs by timeout so the daemon can record a comparable timedOut flag.

### [LOW] `snapshot` produces different artifacts per engine (aria tree vs raw outerHTML) yet both are journaled under the same command name and latency-compared
- **Where:** `stealth/extensions/nightcrawl-bridge/background.js:79-80 vs src/snapshot.ts:212/244`
- **Evidence:** recordEngineOutcome treats `snapshot` as a routing-signal command for BOTH engines (server.ts:1380 `if (!NAV_COMMANDS.has(command) && command !== 'snapshot') return`). But headless `snapshot` runs Playwright `ariaSnapshot()` with a 5s internal timeout + DOM parsing (snapshot.ts:244, read-commands.ts:171), while Engine R `snapshot` is `document.documentElement.outerHTML` via one CDP Runtime.evaluate (background.js:80) — a much cheaper, different operation. Their latencies are recorded into the same per-engine medianLatencyMs (engine-journal.ts:143-150) and compared by recommendFromStats. outerHTML on a large DOM and an aria tree have unrelated cost curves, so the snapshot-latency contribution to the recommendation is comparing two different workloads labeled identically.
- **Proposed fix:** Either exclude `snapshot` latency from the cross-engine ranking (keep snapshot only for the success/relogin/axTimeout signals, not latency), or normalize: have Engine R's snapshot do an equivalent accessibility extraction so the artifact and cost match. Simplest correct step: in recommendFromStats, compute the latency tiebreak from `goto`-only records, since goto is the one command with comparable semantics on both engines.

### [LOW] medianLatencyMs pools goto, back, forward, reload AND snapshot into one number — a domain hit mostly by one command on engine A vs another on engine B compares unlike workloads
- **Where:** `stealth/browser/src/engine-journal.ts:143-151`
- **Evidence:** aggregateByEngine groups records by engine only, then `const okLatencies = oks.map((r) => r.latencyMs)` and `medianLatencyMs: median(...)` (engine-journal.ts:143,150) — it never partitions by command. A `goto` (full page load) and a `snapshot`/`reload` have very different baseline costs. If on a given domain the agent ran 5 gotos on headless but 5 snapshots on Engine R (common, since the agent navigates with headless then reads with Engine R or vice-versa), the per-engine median latencies reflect different command mixes, not engine speed. recommendFromStats then ranks those non-comparable medians (engine-journal.ts:169) and the latency tiebreak is meaningless.
- **Proposed fix:** Partition latency by command when aggregating (e.g. compute medianLatencyMs over `goto` records only, since NAV_COMMANDS.goto is the canonical comparable workload), or carry a per-command latency map in EngineStats and have recommendFromStats compare only matching commands. The success-rate axis can stay pooled; only latency needs command-level partitioning to be comparable.

### [LOW] All latency uses Date.now() (wall clock) — NTP steps / sleep-wake skew can produce negative or wildly inflated latencies that poison the median
- **Where:** `stealth/browser/src/server.ts:1413,1484,1490; engine-journal.ts (median has no guard)`
- **Evidence:** Latency is `Date.now() - startedAt` everywhere (server.ts:1413,1484,1490). Date.now() is wall-clock and non-monotonic: if the OS clock steps backward during a long nav (NTP correction, or the laptop sleeps mid-goto — common for a background 'digital twin' daemon), latencyMs can be negative or hugely inflated. engine-journal.ts median() (lines 125-130) does no sanity clamp, so one sleep-spanning nav can dominate the median for that engine and flip the recommendation. The daemon is explicitly long-lived/background (the whole product premise), making sleep-wake skew likely.
- **Proposed fix:** Measure durations with a monotonic clock (`performance.now()` or `process.hrtime.bigint()`) for the elapsed computation, keeping Date.now() only for the record `ts`. Optionally clamp/drop non-positive or absurd (>5min) latencies in recordEngineOutcome before journaling.

### [LOW] Engine R goto journals the REQUESTED url's domain, not the post-redirect landing domain — outcomes can be attributed to the wrong domain
- **Where:** `stealth/browser/src/server.ts:1481-1484`
- **Evidence:** In routeToBridge, `const url = (body.command === 'goto' && body.args?.[0]) ? body.args[0] : browserManager.getCurrentUrl()` (server.ts:1481) — for a goto it uses the literal argument URL. recordEngineOutcome then keys the journal on `eTldPlusOne(url)` of that requested URL (server.ts:1383). But the bridge's goto follows redirects and updates `bound.url` to the FINAL url (background.js:282). So a goto to a short-link / SSO entry that lands on a different eTLD+1 gets its latency/success attributed to the SOURCE domain, not where it ended up. Headless has the same shape (server.ts:1381) but at least its getCurrentUrl() reflects the real page for non-goto commands; on Engine R, browserManager.getCurrentUrl() is the HEADLESS page (a different browser entirely), so the fallback branch is also wrong for any non-goto Engine R command — it reads the headless browser's URL to label an Engine R outcome.
- **Proposed fix:** Have the bridge return the final URL in its goto result payload and use THAT for the journal domain. For non-goto Engine R commands, the daemon must not fall back to browserManager.getCurrentUrl() (the headless page) — track the bound-tab URL reported by the bridge (e.g. via bridge-tabinfo or by caching the last goto's final URL per bridge session) and key the journal on that.

## accuracy-deliverable

### [HIGH] `verify page` always checks the HEADLESS page, never Engine R's real tab — DVC verifies the wrong browser
- **Where:** `stealth/browser/src/meta-commands.ts:283-291`
- **Evidence:** case 'verify' → mode 'page' does: `const page = bm.getPage(); const url = page.url(); const text = await getCleanText(page); const result = verifyPage(url, text, parsed.page);`. `bm.getPage()` is ALWAYS the headless CloakBrowser page. There is no branch for `--engine=real`. When an agent does its real work on Engine R (the user's live Arc tab — server.ts:1957 routeToBridge), the actual result lives in the Arc tab, but `verify page` inspects the headless page, which is typically on about:blank or a stale/logged-out URL. The deliverable-verification contract — the one mechanism whose entire job is to stop 'reported success without the real result' — itself reports against a page the work never touched. A `verify page --url-includes ... --text-includes ...` can PASS on stale headless content or FAIL on an empty headless page while the real Engine-R deliverable is correct (or vice-versa). This silently defeats the DVC for every Engine-R task.
- **Proposed fix:** Make `verify page` engine-aware. Accept `--engine=real` (or read body.engine) and, when set, pull the URL+text from the bridge: `bridgeHub.dispatch('js', ["location.href"])` and `bridgeHub.dispatch('text', [])` instead of `bm.getPage()`. Better: route the whole `verify page` through the same engine the caller names so the DVC always inspects the page the agent actually drove. If no bridge is connected and engine=real was requested, fail loudly (VERIFY_FAILED: real-browser not connected) rather than silently checking headless.

### [HIGH] Engine R reads (text/html/snapshot) skip hidden-element stripping AND the untrusted-content trust boundary
- **Where:** `stealth/browser/src/server.ts:1957-1958 + 960-965`
- **Evidence:** The headless read path wraps content: server.ts:961-965 `result = await handleReadCommand(...)` then `if (PAGE_CONTENT_COMMANDS.has(command)) result = wrapUntrustedContent(...)`, and `handleReadCommand`'s text case calls `getCleanText` → `stripHiddenElements` (read-commands.ts:88-95) which strips CSS-hidden prompt-injection nodes. The Engine R path returns BEFORE any of this: server.ts:1957 `if (body?.engine === 'real' && isBridgeCommand(...) ) return await routeToBridge(body, startedAt);` and routeToBridge (server.ts:1485) returns `new Response('[real-browser] ' + text, ...)`. The bridge `text` is raw `document.body.innerText` (bridge-commands.ts:44-45, background.js:78) — no stripHiddenElements, no `--- BEGIN UNTRUSTED EXTERNAL CONTENT ---` markers. So on Engine R the agent receives third-party page text with NO injection stripping and NO trust boundary, while the same command on headless is sanitized + fenced. Identical-looking command, two different fidelity/safety contracts.
- **Proposed fix:** Apply the same post-processing to bridge read output: in routeToBridge, when `PAGE_CONTENT_COMMANDS.has(body.command)`, run the returned text through `wrapUntrustedContent(text, landedUrl)`. For hidden-element stripping, either inject the stripHiddenElements logic into the bridge's `text` evaluate expression, or have the bridge return outerHTML and strip server-side. At minimum the untrusted-content fence must wrap Engine-R page content — it is a security boundary, not a nicety.

### [MEDIUM] Engine R `snapshot` returns raw outerHTML instead of the @ref accessibility tree the agent is told to click
- **Where:** `stealth/browser/src/bridge-commands.ts:47-49 + extensions/nightcrawl-bridge/background.js:79-80`
- **Evidence:** Headless `snapshot` (snapshot.ts:5) produces a YAML-like ariaSnapshot tree with `@ref` handles — the nightcrawl skill explicitly instructs: 'Use snapshot (NOT screenshot)... snapshot gives structured DOM with @refs you can click/fill directly.' But the bridge maps snapshot to plain HTML: bridge-commands.ts:48-49 `case 'html': case 'snapshot': return evaluate('document.documentElement.outerHTML')` and background.js:80 identically. So on Engine R, `snapshot` silently returns megabytes of raw outerHTML with NO @refs. A subsequent `click @ref3` cannot resolve (the bridge's click only does `document.querySelector(selector)`, background.js:84-87) — the agent thinks it has a snapshot and refs, gets HTML, and any @ref-based action fails or, worse, silently no-ops. The command name promises one contract and delivers another on the real engine.
- **Proposed fix:** Either (a) implement a real accessibility snapshot in the bridge via CDP `Accessibility.getFullAXTree` and emit @ref handles compatible with the headless format, or (b) if that's out of scope, make the bridge REJECT `snapshot` with an explicit error ('snapshot not supported on --engine=real; use text/html') so the agent fails loudly instead of receiving mislabeled HTML. Do not let `snapshot` return HTML under the snapshot name.

### [MEDIUM] Engine R goto records success/win against the requested URL, not the URL it actually landed on (login redirects count as wins)
- **Where:** `stealth/browser/src/server.ts:1481-1484 + 1385`
- **Evidence:** routeToBridge: `const url = (body.command === 'goto' && body.args?.[0]) ? body.args[0] : browserManager.getCurrentUrl(); if (url && url !== 'about:blank') recordWin(url, 'real'); ... recordEngineOutcome(body, 'real', 200, text, ...)`. For goto it keys off `body.args[0]` — the REQUESTED url — and the bridge's goto return string is just `navigated to <url>` (background.js:283), which never contains 'LOGIN_REQUIRED'/'CONSENT_REQUIRED'. recordEngineOutcome sets `ok: status===200 && !reloginRequired` (server.ts:1393), and reloginRequired is regex-matched from text (line 1385) that the bridge never emits. Net effect: a goto that redirected the real Arc tab to an SSO/login/error page is recorded as ok:true AND `recordWin(targetDomain,'real')`. The learned router (engine-routing) then recommends Engine R for that domain based on a phantom success. The headless path at least runs detectLoginWall (server.ts:1094) and appends LOGIN_WALL/LOGIN_REQUIRED before recordEngineOutcome reads it; Engine R has NO login-wall detection at all.
- **Proposed fix:** Key the bridge outcome on the ACTUAL landed URL, not the arg. Have the bridge return the final `tab.url` after waitForLoad (background.js already reads `t.url` at line 282 — surface it in the result), and in routeToBridge use that landed URL for both recordWin and recordEngineOutcome. Additionally, run a lightweight login-wall/redirect check on the landed URL (reuse the loginRe in server.ts:1277 or a bridge-side check) and set reloginRequired accordingly so a redirect-to-login is recorded as a failure, not a win.

### [MEDIUM] Engine R reads after a non-goto navigation hit a half-rendered page — only goto waits for load
- **Where:** `stealth/extensions/nightcrawl-bridge/background.js:271-291`
- **Evidence:** In execute(), `waitForLoad(tabId)` is called ONLY inside the `if (command === 'goto')` branch (background.js:275-281).
